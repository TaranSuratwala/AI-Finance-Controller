The Fintech Dilemma

Why Traditional AI Breaks in B2B Reconciliation

1. Unstructured Payment Memos Real-World Input
"Settlement for INV-100 (Total: 400), and INV-101 (Total: 600) minus 2% gateway fees. Ref: TXN_9988_PARTIAL"
  • ✕ Regex Fails: Format changes, typos, delimiters, and invoice groupings break fragile rules.
  • ✕ Delimiters Madness: Slashing, double hashes, and concatenated invoice numbers.
2. The Hallucination Trap Catastrophic Risk
"AI Calculation: 400 + 600 = 1000 - 20 = 980. Result: Settled. (Actually short by 50 paise in reality!)"
  • ✕ LLMs Cannot Do Reliable Math: Probabilistic token generation inherently miscalculates decimals.
  • ✕ False Positives Are Fatal: Marking an unpaid invoice as settled causes permanent ledger leakage.
💡 The Core Rule of Fintech AI: Never allow an LLM to calculate the final financial truth.
System Architecture

The Dual-Layer Zero-Hallucination Engine

GATE 0

FastAPI Ingestion

Verifies X-Razorpay-Signature (HMAC SHA-256). Extracts x-idempotency-key. Returns instant 200 OK to gateway.

LAYER 1

AI Auditor (Gemini)

Extraction ONLY. Extracts invoice IDs & stated gross totals into strict Pydantic schemas. Forbidden from final math.

LAYER 2

Deterministic Gate

Python Rules Engine recalculates fee schedules, checks tolerance down to 50 paise, atomic Redis locks, and ERP state.

OUTCOME

Audit or Settle

Passed transactions hit the Master Ledger. Rejected transactions enter Immutable Audit DB for FinOps & Merchants.

🛡️
Resilient Degradation Fallback
If Gemini API limits (HTTP 429) hit, the service routes through deterministic regex fallback with confidence tagging. Zero downtime.

4 High-Stakes Scenarios in Action

Case A: Messy Multi-Invoice Settlement PASSED

"INV-100 (Total: 400.0), INV-101 (Total: 600.0)"

Even if AI advisory split varies, Gatekeeper independently calculates the gross sum (1000.0) and validates with 2% fee. Reconciled straight-through.
Case B: Amount Mismatch (51 Paise Discrepancy) SAFELY BLOCKED

Payload amount: 980.51 vs Invoice total: 980.0

Exceeds the 50-paise tolerance threshold. Gatekeeper blocks the transaction and logs forensic audit entry. Zero financial leakage.
Case C: Stale ERP State (Closed Invoice) SAFELY BLOCKED

Settlement attempts to credit already-closed invoice INV-999.

Gatekeeper checks ERP state before posting. Blocks double settlement and routes to Merchant Support Portal for reopening.
Case D: Replay Attack / Duplicate Webhook IDEMPOTENCY CAUGHT

Identical webhook payload sent twice with same idempotency key.

Redis atomic SET NX detects duplicate key. Second request is instantly blocked, preventing double-crediting.
